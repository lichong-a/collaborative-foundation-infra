# 工程结构与业务边界

[返回入口](../SKILL.md) · [会话选择](session.md)

本规范独立于交付模式；devflow 与 basic 都必须遵守，不以是否启用四角色决定工程质量。

为现有目录建立责任地图：业务模块、共享领域能力、基础设施适配、测试、生成物、文档和部署。先从入口、依赖清单、测试和代码确认事实；不以模板强制把旧仓移动成固定布局。

每个模块写清职责、公开接口、允许依赖方向、数据所有者、副作用所有者和负责审核者。业务专属状态、展示和流程留在所属模块；通用层不能依赖具体客户或页面。新增模块前证明现有模块无法合理承担职责。

共享代码变更先说明必要性、受影响调用方、兼容方案和回归范围，并按任务批准范围执行。不得通过改全局默认、公共拦截器或放宽检查满足单一业务。

接管顺序：只读画像 → 既有流程映射 → 文档/路径债务登记 → 确定性整理预览 → 授权范围内应用 → 检查复跑。文件归属、合并与移动由人或独立 Agent review 决定。

根级和模块级 AGENTS 只路由相关事实，不复制全量规范。代码、文档、生成物各有明确入口，所有非显然结构决定回到既有 Spec/Decision。

检查器只检查明示目录和扩展名规则；已登记目录不等于架构已被认可。未配置的依赖方向和业务归属需要代码审核。

## 新项目与现有项目

新项目先根据需求、实际语言/框架、部署方式和数据所有权推荐最小目录树，同时说明每个模块职责、公开接口、依赖方向、测试位置、生成物和文档入口。将这个推荐纳入当前方案确认，不新增架构师、独立批准链或强制目录模板；后续变化回到原有设计或 Decision。

现有项目先画像，再给最小调整建议；已有架构或画像入口就复用，没有时才在获准路径补最短说明与导航。结构混乱不授权自动移动、合并、删除或大面积重写。业务行为、用户未提交内容、保护路径与原流程事实源持续保留。
